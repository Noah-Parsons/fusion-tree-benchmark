# ClusterJump against Hist-Tree (CHT) and RMI: plan, fixed before any download or timing

Written 2026-09-13, after reviewer feedback that the static ClusterJump
results lacked the two baselines that matter most:

- **Hist-Tree** (Crotty, CIDR 2021), in its compact read-only form CHT. It
  is architecturally close to ClusterJump (a multi-level histogram over key
  bits; see `results/RELATED_WORK.md`).
- **RMI** (Kraska et al., SIGMOD 2018), which typically has the lowest lookup
  latency on SOSD, and latency is where ClusterJump already loses.

## Questions

1. How does ClusterJump differ from CHT, and which is faster?
2. Does the ClusterJump throughput claim survive RMI and CHT?
3. How far behind is ClusterJump in latency against the strongest known
   competitors?

## Racers

- `clusterjump`, `splus8`, `splus16`, `rs18_e16`, `pgm16`: unchanged.
- **CHT**: the implementation used by PLEX and SOSD
  (github.com/stoianmihail/CHT, MIT), in read-only compact layout.
- **RMI**: code generated by the reference RMI tool
  (github.com/learnedsystems/RMI, MIT), trained on exactly the keys each
  session races on (`bench_pred ... dump:<path>`). SOSD's pre-trained RMIs
  cannot be reused: they index the full 200M-key files, while this race uses
  2^25 keys sampled per session.
- Both finish with the same final search step as every other structure here.
- SOSD's own wrapper code is GPL-3.0 and is **not** copied into this MIT
  repository; wrappers are written fresh from the libraries' public APIs.

## Dataset facts checked before the race

From the full SOSD files (all sorted): books 200M keys, no duplicates, max
about 2^63. wiki 200M keys, **109,562,989 duplicates** (about 90.4M distinct,
still more than 2^25). fb 200M keys, no duplicates, and its largest key is
**UINT64_MAX**, the value PGM-index reserves as a sentinel; its wrapper already
handles this. osm 200M keys, no duplicates. Every structure here is built on
distinct keys, and RMIs are trained on the same distinct keys.

The exact 2^25 key sets for seeds 20260909–12 are written once by
`bench_pred ... dump:data/samples/<dataset>_<seed>` (not in git) before any
RMI is trained. The dump does not change the random sequence, so the race
uses identical keys.

## Setup record (before any timing)

- CHT: 12 settings; `tests/test_structures.cpp` covers two of them; 27,600,000
  checks in all, zero failures.
- RMI: the optimizer returned 10 Pareto configurations per dataset
  (`data/rmi/optimize/opt_<dataset>.json`), from 3 KB to about 400 MB. All 40
  were trained on the seed-20260909 keys and generated
  (`analysis/rmi_build.sh`, `data/rmi/manifest.csv`).
  `tests/test_rmi.cpp` checked each against std::lower_bound on 2,000,000
  queries per dataset, half on stored keys and half between them: **80,000,000
  checks, zero wrong answers.**
- Several small configurations have a worst-case error near the whole array
  (max log2 error 25 in the optimizer's table). Their searches rely on the
  wrapper's window check, and their times will show it.

## The first Stage 1 attempt crashed the laptop (2026-09-13)

The first attempt ran all 25 Stage 1 structures in one process, straight
after WSL had read and written several GB. About nine minutes in, Windows
stopped with KERNEL_MODE_HEAP_CORRUPTION (0x13A). The crash dump names
`nvlddmkm.sys`, the NVIDIA graphics driver (then 595.79), freeing memory it
had already freed. The same machine had crashed before (20 March 2026, and
unexpected shutdowns on 9 and 16 July). The benchmark does not use the GPU;
the heavy memory load most likely exposed the driver bug. The driver was
updated to NVIDIA Studio 616.92.

Its partial output is kept in `results/sosd_rivals/crashed_run/` and is not
used. The rerun (`analysis/sosd_stage1.ps1`) changes only how the work is
split, not what is measured:

- at most 8 structures per process, each group including both S+ trees and
  ClusterJump, so every ratio is still taken within one run;
- WSL shut down first, a pause between runs, and no run starts with less
  than 6 GB of RAM free;
- a pilot of the heaviest group (the five largest RMIs, osm, one repetition)
  peaked at **4.5 GB** of memory, with at least 15.6 GB free throughout.

## The second attempt pushed memory to 100% (2026-09-13)

The light `bench_pred` rerun (groups of at most 8 structures) finished all ten
books runs and two wiki runs, with process peaks of 3.8–4.5 GB, and 8.7 GB for
the group holding the four CHT settings with 1024 bins. During that same group
on wiki, Windows memory reached 100% and the user stopped the run. The
checks between runs could not catch this, because the growth happens inside a
single CHT build. CHT's builder keeps a node of `bins` counter pairs for every
split bin, so with 1024 bins and a small error bound on dense keys (wiki
timestamps) the temporary tree runs to many GB. Those partial results are in
`results/sosd_rivals/stopped_run_bench_pred/` and are not used, so that every
Stage 1 number comes from one harness.

## Harness change: bench_one (before any Stage 1 data is used)

`bench/bench_one.cpp` measures the same thing as `bench_pred` with the timed
loop copied unchanged, but races only the 2^25 sample, keeps one structure in
memory at a time (build, warm, time, destroy, in a fresh random order each
repetition), and runs under a Windows job-object cap of 8 GB of committed
memory. A structure that needs more is recorded as `OVER_MEMORY_CAP` and
skipped. `analysis/sosd_stage1.ps1` also stops the run if free RAM falls
below 6 GB.

Two tests, run with the user's permission before any campaign:

- **cht1024_e16 on wiki:** hit the cap and was skipped (`OVER_MEMORY_CAP`);
  process peak 7.87 GB, lowest free RAM 17.5 GB, 5 seconds.
- **splus8, splus16, clusterjump, rs18_e16, pgm16 on books:** peak 0.54 GB,
  2 seconds, identical checksums.

**Consequence for selection.** A setting recorded as over the cap on any
dataset has no Stage 1 result there, so `sosd_select.R` (which requires all
four datasets) cannot choose it. Such settings are reported as needing more
than 8 GB to build a 2^25-key index. That is itself a result: the builder
holds 8 bytes per bin per node, and the finished table keeps 4, so such
settings would also produce indexes of several GB.

## Third attempt: one bench_one process per dataset stopped on wiki

With the full race approved, `bench_one` completed books in both modes (peak
5.36 GB, lowest free RAM 19.3 GB, no settings over the cap). On wiki the
process ended after 7 seconds with STATUS_STACK_OVERFLOW (exit -1073741571)
at a peak of 7.88 GB, just under the 8 GB cap. Most likely a CHT build reached
the cap at a moment the thread needed to commit a new stack page, so Windows
raised a stack overflow instead of the allocator reporting out of memory. The
laptop was never at risk (16.8 GB free).

Fixes, before any wiki data was kept:
- **Pre-flight:** each CHT setting is built alone, in its own process, once
  per dataset, timing nothing. Settings that do not fit under the cap, or
  whose process dies, are excluded from that dataset's timed runs and logged.
- The harness commits 8 MB of stack at link time, so the stack never needs
  new memory mid-run, and it logs the name of each structure before running
  it.
- The books results from this attempt come from the same harness and
  settings (no CHT was over the cap on books), so they are kept.

## Not raced, with reasons

- **FAST** (Kim et al., 2010): no public original implementation. SOSD's
  version is a GPL reimplementation. The S+ tree raced here is FAST's
  direct descendant: a pointer-free, SIMD-searched static B+ tree.
- **ART** (Leis et al., 2013): SOSD's copy supports only exact-match lookup,
  not the lower bound this study needs, and has no licence header. In the
  Hist-Tree paper ART is slower than RMI, RadixSpline and CHT on three of
  four SOSD datasets. Stated as untested, not as beaten.

## Stage 1: tuning (exploratory), seed 20260909, 7 repetitions

- **CHT:** bins ∈ {64, 256, 1024} × max error ∈ {16, 32, 64, 128}
  (12 settings; covers the SOSD sweep's range).
- **RMI:** the RMI tool's own optimizer (`--optimize`) run on each dataset's
  tuning keys, producing its Pareto-optimal configurations; all of them are
  raced. SOSD's tuned `rmi_specs` grids are used as well if the optimizer
  output is smaller than 4 configurations.
- **Clarification for RMI, added after the optimizer was chosen and before any
  timing.** The optimizer proposes a different architecture for each dataset
  (model types and branching factor), so "the same setting on every dataset"
  cannot mean the same architecture. For RMI a setting is a **rank on that
  dataset's Pareto list, ordered by model size** (rank 1 = smallest). The rule
  below then chooses one rank per mode.
- **Selection rule (unchanged from `results/learned/PLAN.md`):** separately
  for each library and each mode, at 2^25, choose the setting with the
  lowest geometric mean over books, wiki, fb and osm of time ÷ the faster
  S+ tree. Ties within 2%: less memory.

## Stage 2: confirmation, seeds 20260910–12, 15 repetitions

- `clusterjump`, `splus8`, `splus16`, `rs18_e16`, `pgm16`, the chosen CHT
  setting(s) and the chosen RMI(s), per mode.
- An RMI is regenerated for each session's keys with the chosen
  configuration.
- **Claim rule (unchanged):** in each cell (dataset × mode) at 2^25,
  ClusterJump beats a rival if faster in all three sessions, loses if slower
  in all three, otherwise ties. Every cell is reported, and memory per key
  alongside.

## Expectation, written before anything was downloaded

- **Latency:** RMI and CHT both beat ClusterJump on all four datasets, by
  more than RadixSpline and PGM did.
- **Throughput:** ClusterJump stays ahead of RMI (a longer search, with
  several models and a wide error window on hard datasets), but **CHT may
  match or beat it**. CHT's search is a short loop of shifts and table reads,
  close to ClusterJump's own.
- If CHT matches ClusterJump in throughput, ClusterJump's only remaining
  claim is being simpler, and that is not a performance claim.
